1. Executive Summary

Epsu is a mobile-first anonymous community application centered around place-based communities called Epsus. The app currently supports account creation, posting, replying, swiping to rate posts, reporting posts, moderator review, higher-level community management, account-history export, deletion, and legal documentation. It is built as an Expo and React Native client backed directly by Supabase.

The app is no longer a bare minimum prototype. It is a real early product with a meaningful amount of business logic, governance logic, and user-account handling. At the same time, it is still not best understood as a mature production platform. It has real capabilities, but it is still in a stabilization phase.

Real today
Anonymous posting, replies, swipe reactions, reporting, moderator queues, host-level management tools, audit logs, account history, export, deletion, keyword-based pre-submit warnings, and a live Supabase schema with migrations.
Planned, not yet implemented
Paid host terms for school Epsus, regional advertising, fuller host transfer and replacement policies, stronger case-management support for admin review, and broader commercial operations.

2. Current Status of the Product

The most accurate description of Epsu at this point is: an early product with real operations, not just an MVP, but still not finished enough to be called a mature public platform.

Reasons it is beyond MVP:

  • It already has multiple community types, not just one feed
  • It has governance layers: users, moderators, hosts, and admin
  • It has legal pages, account-history tools, export, and deletion
  • It has safety tooling beyond simple reporting, including keyword warning prompts and governance logs

Reasons it is not yet mature:

  • It still needs more operational tooling and more testing
  • Some product and governance rules are still being defined while the code is already live
  • iOS capability is partly constrained by build-signing realities, not just code
  • The platform still needs stronger commercialization and support workflows before broad launch

5. System Overview

5.1 Product model

The product model is straightforward:

  • A user creates an account with email and password
  • The user joins or applies to Epsus, which are communities tied to place or institution
  • The user posts anonymously inside an Epsu
  • Other users rate posts by swiping left or right
  • Users can reply and report
  • Moderators and hosts manage abuse and governance
  • Admin remains above hosts and moderators

5.2 Community types

Type Current purpose Current access pattern Commercial relevance
Regional Epsu City, country, or regional discussion Usually joinable or suggested by users Potential future ad inventory
School Epsu Institution-specific discussion and governance Application or membership driven Most likely first paid host model

6. Technology Stack

6.1 Client stack

Based on package.json and app.json, the main stack is:

  • Expo SDK 54
  • React 19.1
  • React Native 0.81
  • React Navigation 7
  • Supabase JavaScript SDK 2.x
  • AsyncStorage for local persistence
  • Expo Notifications, Image Picker, Image Manipulator, File System, Sharing, and Image
  • React Native Gesture Handler and Reanimated for gesture-driven UI

6.2 Backend model

There is no custom application server in this repository. Supabase provides authentication, Postgres, RPC execution, storage, and API access. That means the trust model depends heavily on database policy, RPC design, and migration quality.

6.3 Public and legal surface

The repository also contains a static site under site/. This includes the Terms of Service, Privacy Policy, Community Guidelines, and landing pages. The system report you are reading is intended to sit alongside those documents.

7. Current Application Architecture

7.1 Present architecture shape

The app used to be much more monolithic. It has now been split into clearer pieces, but it still uses a custom architecture rather than a formal framework like Redux Toolkit or React Query.

Main current architectural pieces:

File or module Purpose
app.js App shell, state ownership, navigation, context provider composition
AppContext.js Split app context into session, data, and actions
lib/createAccountActions.js Account and authentication actions
lib/createCommunityActions.js Feed, moderation, and community actions
lib/useAppBootstrap.js Session hydration and initial data loading
lib/useAppNotifications.js Unread notification prompt, sync, and display flow
lib/useEpsuPresence.js Presence refresh and population updates
lib/appStateTransforms.js Pure helper functions for state changes
lib/api/epsus.js, feed.js, moderation.js, account.js Feature-specific data access layer

7.2 Why that matters

This matters because the app had already shown the classic symptoms of too much logic too high in the tree: input focus dropping, keyboard closing after a single character, visual flicker, and unrelated features breaking one another. The recent architecture work reduced that risk by splitting concerns.

7.3 Comparison to common large React Native practice

Compared to stronger React Native app architectures, Epsu is now in a respectable intermediate state. The root has been cleaned up, the API layer is split by feature, and context is narrower. However, it still does not have the deeper entity modeling, feature stores, selectors, and automated test coverage typical of more mature systems.

8. Data Model and Stored Information

The database schema lives in supabase/schema.sql and migrations under supabase/migrations/. The exact live schema is migration-driven, but the main data categories are stable.

8.1 Main record groups

Record type Purpose
Profiles Username, country, date of birth, notification and guideline acceptance fields
Epsus Community records with scope, name, slug, country, review status, website, and logo path
Memberships User membership, role, status, and mute information by Epsu
Posts Anonymous community posts with reply linkage and counts
Post reactions One reaction per user per post
Post reports User reports tied to posts
Moderation actions Audit log for moderation and major host actions
App notifications In-app notifications for review, school, and flagged content events
Suggestions and applications Epsu suggestions, school join applications, and account requests

8.2 Data minimization reality

The product is anonymous at the community-facing level, not anonymous in the database. The app stores author identifiers, membership identifiers, moderator action identifiers, and reporting relationships. That is operationally necessary for moderation, deletion, safety, and governance, but it means the app should not be described as "truly anonymous in storage."

9. Identity, Accounts, and Authentication

9.1 Authentication

Authentication is handled through Supabase Auth with email and password. Session restoration is performed during bootstrap. Profile fields are then hydrated from the profiles table and merged with auth metadata if needed.

9.2 Age gate

The client includes a minimum age rule at signup. It is a client-side enforcement point today, which is good for product flow but weaker than server-backed verification.

9.3 Account state loaded at login

On successful hydration, the app loads:

  • Profile identity fields
  • Epsu catalog
  • Posts
  • Reviewed and reported post identifiers
  • Memberships and hidden Epsu state
  • Moderated and host-managed Epsu identifiers
  • Open reports for communities under the user's management
  • Population counts

10. Posts, Replies, Ratings, and Reports

10.1 Posting

Posts are created through a database RPC. The client creates new posts through a structured action flow, not raw SQL. A post can optionally reference another post as a reply target. The app includes specific handling so a reply whose parent was deleted can still degrade into a normal post instead of hard failing.

10.2 Reply context

Replies show the original referenced post above the active reply post in the feed so users can understand context. This was added because the old "Reply to #number" pattern did not explain what was being answered.

10.3 Rating

The current rating model is Tinder-style swipe interaction. Swiping right means like; swiping left means dislike. This replaced the earlier double-tap-side interaction because swipe is more legible and closer to users' expectations.

Rating is not only cosmetic. The current live crowd-moderation threshold is:

  • At least 100 total ratings on a post
  • At least 60% dislikes among those ratings

When both conditions are met, the post is moved to deleted_by_threshold. This is a real implemented mechanic in the database reaction flow, not just a product idea.

10.4 Reports

A user can report a post. Reports are visible to moderators and hosts with the relevant rights. The system tracks open reports and allows dismissal, removal, and mute actions.

10.5 Keyword warning flow

The current app also contains a pre-submit keyword warning system. It does not attempt to understand context. Instead, it looks for a list of flagged terms. If a user is warned and still chooses to post unchanged, the system can notify moderators or hosts. This is intentionally blunt and is treated as a safety tripwire, not a final judgment engine.

Important limitation
The keyword filter is not intelligent semantic moderation. It is a large string-matching warning list. This reduces implementation complexity but creates false positives.

11. Automated and Crowd Moderation

11.1 Crowd-removal threshold

Epsu currently includes a direct crowd-based moderation mechanic. When a post reaches at least 100 total ratings and at least 60% of those ratings are dislikes, the database reaction flow moves the post into deleted_by_threshold.

This is a real automatic moderation rule. It is not just an analytics metric and it is not just a UI hint. Once the threshold is crossed, the post is no longer treated as active content in the normal feed.

11.2 Why this matters

  • It creates a genuine automated moderation outcome
  • It can affect user speech without a moderator clicking remove
  • It therefore belongs in any serious governance or risk review of the product

11.3 Human backstops around it

The threshold rule does not stand alone. The current surrounding moderation layers are:

  • User reports
  • Moderator review queue
  • Moderator dismissal, removal, and mute actions
  • Host-level governance and audit visibility
  • Admin oversight above hosts and moderators

11.4 Limits of the current crowd rule

  • It does not understand context
  • It is vulnerable to coordinated down-rating if a community is unhealthy
  • It does not distinguish between harmful content and unpopular content
  • It only activates after a post has already reached substantial engagement

11.5 Current assessment

The threshold is simple and easy to explain, which is a strength. It is also blunt, which is a risk. In a regulator, auditor, or investor conversation, it should be described honestly as crowd-based automatic moderation with human moderation layers around it, not as a fully reasoned safety system.

12. Moderation, Governance, and Host Powers

12.1 Current role layers

The practical role layers are:

  • Regular user
  • Moderator
  • Host
  • Admin

In the database and route naming, the internal role is still often stored as owner. In the user-facing product, this is now presented as Host to avoid implying permanent legal ownership over a community.

12.2 Moderator actions

Moderators currently have the main content safety functions:

  • Dismiss reports
  • Remove reported posts
  • Mute reported authors for a fixed period

12.3 Host actions

Hosts currently manage community-level operational actions such as:

  • Reviewing join applications in school Epsus
  • Managing moderators
  • Removing certain members in school communities
  • Generating invites
  • Deleting managed Epsus

12.4 Governance logging

The app now uses a broader audit trail for moderation and major host actions. This matters because a platform cannot responsibly delegate governance without keeping records of who did what, when, and to whom.

The current direction of the logging model is:

  • Moderator actions are logged
  • Major host actions are logged
  • Users can access actions involving them through account history
  • Admin remains the ultimate escalation layer

12.5 Worst-user ranking

The current “worst users” view does not simply count deleted posts. It now uses report-based ranking: a user must have at least one reported post, at least two distinct reporters, and be in the top ten by total report count in that Epsu. This is more defensible than pure deletion count.

13. Account History, Export, Correction, and Deletion

13.1 Account history

The app contains an Account history screen accessible through Settings. This is the main user-facing rights and traceability surface. It allows the user to review data involving them, export it, and request corrections.

13.2 Export

The app can generate a data file representing the account-history data set. On Android this follows a closer-to-download flow. On iOS the complete experience depends on native sharing support in the built app.

13.3 Correction

The app now contains an in-app correction request mechanism. These requests are stored, not just shown as text hints. That means correction is no longer purely aspirational in policy wording.

13.4 Deletion

The delete-account flow is backed by a live database RPC. The system deletes account-linked support data, while some community-history records may remain de-linked where necessary for platform integrity and audit traceability.

Important deletion characteristics:

  • Deletion can be blocked if the user still manages an Epsu
  • Notifications, reactions, reports filed, memberships, and related support records can be removed
  • Posts and governance history may persist in de-linked form where required for community history
  • Logo-related storage cleanup was previously a gap and has been partly addressed in code-side compliance work

14. Security and Trust Boundaries

14.1 Main trust model

Because there is no custom backend tier here, the most important trust boundary is between the mobile client and Supabase. Client code must never be assumed trustworthy. Safety therefore depends on:

  • Supabase Auth
  • Database constraints
  • RPC design
  • SQL permissions and policies
  • Careful migration management

14.2 Real strengths

  • Important operations are handled through RPCs rather than totally free-form table writes
  • There is audit coverage for governance activity
  • Deletion and account history now exist as real behavior, not only policy claims

14.3 Real weaknesses

  • The app still relies heavily on client orchestration
  • There is no custom application server to enforce cross-cutting logic
  • Safety still depends on migration correctness and database permission design
  • Automated regression coverage remains weak

15. Operations, Build, and Deployment

15.1 Mobile builds

The app uses Expo and EAS configuration. Android packaging is straightforward. iOS requires normal Apple signing and build credentials. Some iOS-native capability issues encountered during development were not code defects alone, but build and signing realities.

15.2 Static site

The public legal and informational site is static HTML. This reduces operational complexity for the public documentation surface.

15.3 Live database operations

Migrations are managed through Supabase tooling. In practice, this means schema correctness and migration discipline are part of platform operations, not just development hygiene.

16. Known Risks and Limitations

16.1 Product risks

  • Local/community products live or die by density
  • Small communities can feel empty quickly
  • Bad hosts or weak moderation can destroy trust fast

16.2 Technical risks

  • There is still relatively little automated test protection
  • The codebase is much better structured than before, but not yet deeply industrial
  • Some older internal naming still says owner even when product copy now says host

16.3 Compliance and operational risks

  • Deletion and rights handling are now much stronger, but still depend on real operations around support handling
  • Keyword filtering can create false positives
  • Paid governance models will require a cleaner refund and termination framework than free volunteer moderation

17. Current Real Business Position

This section describes what is real now, not the future plan.

Epsu currently does not operate with a fully implemented commercial engine in the codebase. There is no completed host-billing flow, no finished direct ad-sales system, and no in-app payment operation visible in the current repository. The product contains commercial hints such as a billing area and school creation flow, but these are not the same as a finalized monetization system.

In plain terms: the app has commercial direction, but not yet commercial completion.

18. Planned Monetization and Governance Expansion

This section is planned thinking only. It is not described as present-day implemented system behavior.

18.1 Planned school host model

The strongest planned monetization idea is school Epsu host licensing. The concept is that a qualified student pays for the right to act as host for a school Epsu for a limited term, likely aligned with the school year. This should not be described as ownership. It is better understood as a paid, revocable host term.

Key operational points already identified in planning:

  • Eligibility should require actual student status
  • Annual timing likely follows the school’s primary academic calendar
  • Host term should be revocable for inactivity, abuse, or loss of eligibility
  • Host transfer should include a handoff period near term end where practical
  • Some communities may remain centrally operated if too small to justify sale

This is the most natural monetization path because it matches the product’s governance structure rather than forcing unrelated revenue ideas onto the platform.

18.2 Planned regional advertising

Regional Epsus may eventually support direct local advertising. The preferred direction is first-party, direct sales rather than third-party ad networks. This keeps the ad relationship simpler and better aligned with the community product.

Important planning questions still open:

  • Whether hosts should have any role in local ad sourcing
  • Whether admin retains final control over pricing and approvals
  • How many ad surfaces should exist without harming product trust

18.3 Planned expanded host capacity

Another planned idea is allowing a person to manage more than the current default limit of school Epsus for additional payment. This is weaker than the host-license idea because it risks turning governance into a raw power purchase instead of a trust-based operational role. If this is ever implemented, it should be constrained by quality and capacity rules, not payment alone.

18.4 Planned regional host question

There is also active thinking around regional hosts. This is a much harder trust model than school hosts because local residency is harder to prove than student status. A city or regional host model may need smaller district-based scope, stronger activity requirements, or soft verification instead of strict address proof.

19. Product Commentary and Strategic Judgment

From a product and systems perspective, Epsu is not a joke project and not a fake idea. It has a coherent product thesis: anonymous local communities with layered governance and an eventual paid host model.

The strongest thing about the product is that the monetization idea is native to the product. It is not just “add ads to anything.” School host licensing directly matches the governance structure already present in the software.

The biggest risk is not code. The biggest risk is network density and community quality. Local products fail when they do not become the place people actually check. If Epsu wins one school or one city badly enough, the monetization can become real. If it never wins density, feature count will not save it.

In blunt terms: the idea has real upside, but success depends more on community adoption and governance quality than on adding another fifteen screens.

20. Recommended Next Steps

20.1 Immediate technical steps

  • Split schoolApi.js by feature the same way epsuApi.js was split
  • Add lightweight integration tests for account delete, posting, reporting, and moderation actions
  • Keep tightening terminology so product wording consistently says host where intended

20.2 Immediate governance steps

  • Write a Host Code and Host Performance Standard before paid host terms exist
  • Define refund and removal rules before the first school host term is sold
  • Define emergency replacement flow for failed or abusive hosts

20.3 Immediate compliance steps

  • Keep deletion, export, and correction behavior aligned with the written policies
  • Document retention more concretely by record group as operations mature
  • Establish a durable privacy and support contact channel before broad public scaling
